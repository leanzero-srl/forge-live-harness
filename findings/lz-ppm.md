# lz-ppm-forge — findings & test evolution

App: "LeanZero Management" (Jira PPM). Suite: `scenarios/lz-ppm/*`. Oracle imports lz-ppm's own `cascade-core.js`.

## Live-VERIFIED CORRECT (no bug)
- Cascade engine vs oracle, 3× zero-flake: simple chain, three-link, multi-predecessor, fan-out, milestone, **buffer absorption, buffer exhaustion** (7 fixtures). Seed → index → applyEdit → backend `settle` == oracle.

## BUGS TO FIX (ordered by severity)
Source: adversarial code audit (each adversarially verified against the real code path) + harness live findings. `[code]` = verified by code review; `[live]` = also confirmed live by the harness.

### Blockers
- **B1 [code + LIVE ✓ confirmed] Scheduled hourly refresh uses DEFAULT field ids, not the configured ones → wipes Duration/Buffer/Start/Rank ~1h after every index on non-default-field instances. AFFECTS WOLFAENPAK (Duration=cf_10180, Buffer=cf_10181 are non-default).** `src/triggers/scheduled-refresh.js:54-62` calls `fetchIssuesFrom*` with no `fields` arg → falls back to hardcoded `INDEX_FIELDS` (default ids) → `transformIssue` reads configured ids → null → `saveAllIssues` overwrites with null. **LIVE: fresh index Duration=8 → after running the per-plan scheduled-refresh body, Duration=null (`scheduled-refresh.spec.ts`; hook gained a faithful `refreshPlan` replica).** Fix: `getIndexFields(config.fields)` passed into every fetch (mirror run-index.js).
- **B2 [code + LIVE ✓ confirmed] Scheduled hourly refresh skips hierarchy discovery → drops every descendant row each hour for JQL/board/epic sources.** `scheduled-refresh.js:49-79` omits `discoverDescendants()`; `saveAllIssues` rebuilds the index from source issues only → descendants + their links vanish until next manual index. **LIVE: source JQL `key=PARENT`; full index discovered the subtask (keys = PARENT, SUB); after `refreshPlan` only PARENT remained (`scheduled-refresh.spec.ts`).** Fix: run `discoverDescendants` (or delegate to `runIndexing(planId)`).
- **B3 [code — premise CONTRADICTED live ✗, likely FALSE-POSITIVE; was rated blocker] Plan-protection reads new start from changelog `.to`, which the audit claimed is null for date custom fields → Iron-Clad protection never reverts.** `src/services/plan-protection.js:66` `parseDate(startChange.to)`. **LIVE: changing the Start cf (cf_10015) and reading the changelog shows `.to`="2026-01-05" (POPULATED ISO date), NOT null — so `parseDate(.to)` works and the protection would NOT no-op (`plan-protection.spec.ts`).** CAVEAT: the code reads the Forge `avi:jira:updated:issue` EVENT changelog, not the REST changelog API; that's normally the same data, but confirm the event payload before concluding. **Recommendation: do NOT fix without first capturing a real protection-trigger event changelog — the live evidence says this is not a bug.** (Downgrades B3 from blocker.)
- **B4 [code] getBoardIssues advances startAt by constant 100 with no empty-page guard → skips issues and/or loops to Forge timeout.** `src/services/jira-client.js:237-238` `startAt += 100`, board endpoint caps 50/page. Fix: `startAt += issues.length` + break on empty page.

### Major
- **M1 [code] Apply-time conflict check is fail-open and never reads Jira → two users silently overwrite each other.** `concurrency-resolvers.js:61-69` returns no-conflict when no per-user draft (client never calls `saveDraft`); `change-detector.js` diffs KVS vs the user's OWN staged edit, never re-fetches Jira; `write-resolvers.js` imports `detectConflicts` but never calls it. Fix: re-fetch affected issues under the lock and compare live vs start-of-edit baseline.
- **M2 [code] completeWrite returns success + bumps version/re-index even when post-write verify finds mismatches → silent dropped-write loss.** `write-resolvers.js:139-176/234-276` never branches on `verifyResult.mismatches`. Fix: treat mismatches as partial failure (retry, don't clobber `_original`, gate version bump).
- **M3 [code] writeChunk writes with no lock-ownership check and ignores refreshLock failure → concurrent double-write.** `write-resolvers.js:44-96`. Fix: abort if `existing.accountId !== accountId`/expired; honor `refreshLock`.
- **M4 [code] acquireLock is non-atomic check-then-set (TOCTOU) → two users both hold the write lock.** `write-lock.js:21-44` plain KVS get/set. Fix: compare-and-set / transactional KVS.
- **M5 [code + LIVE ✓ confirmed] Non-buffer cascade of a due-but-no-duration issue → duration 0 and inverted due<start (unclamped).** `chain-calculator.js:104-110`; when new iron-clad start passes old due, `calculateDuration` returns 0, due unchanged. **LIVE: A (due 02-27) Blocks B (due 01-07, no duration) → settle returned B `start=2026-03-02 due=2026-01-07 duration=0` — inverted bar (`cascade-pathological.spec.ts`).** Fix: move due forward + clamp `Math.max(1,…)`; enforce start≤due.
- **M6 [code + LIVE ✓ confirmed] Parent roll-up → duration 0 and due<start when a parent predecessor pushes start past all children's due.** `parent-rollup.js:100-102`. **LIVE: parent P (subtask child due 01-09) blocked by A (due 02-27) → settle returned P `start=2026-03-02 due=2026-01-09 duration=0` (`cascade-pathological.spec.ts`).** Fix: clamp + set rolled-up due to effectiveStart when start>latestDue.
- **M7 [code — NOT reproduced live ✗] PHASE 4 snaps start to next working day without recomputing due/duration → trio inconsistent, bar drifts on next recalc.** `chain-calculator.js:127-130`. **LIVE: a weekend-start edit (Sat 2026-01-03) settled to a CONSISTENT trio — start snapped to Mon 01-05, due recomputed to Fri 01-09, duration 5, workingDays(start,due)===duration (`working-days.spec.ts`).** Likely an audit false-positive (the engine recomputes correctly); deprioritize. Fix (if a path is later found): recompute due/duration after normalizing start.
- **M8 [code + LIVE ✓ confirmed] A malformed date string crashes the whole recalculation (no try/catch).** `working-days/calculator.js:15-28`: `parseDate` returns truthy Invalid Date for a non-empty bad string → `formatDate.toISOString()` throws RangeError → `recalculateFullPlan` rejects, plan→'error'. **LIVE: applyEdit a bad `startDate` then `settle` → 500 for all 3 of `2026-13-01`, `bad-date`, `2026/02/15` (`recalc-robustness.spec.ts`).** Fix: `parseDate` returns null on `isNaN(getTime())`; wrap each `calculateIssue`.
- **M9 [code] updateIssuesInShards "batch of 5" throttle is a no-op → all shard writes fire at once.** `kvs-store.js:200-227` (eager `.map(async…)`). Fix: build thunks, `await Promise.all(batch.map(fn=>fn()))` per slice.
- **M10 [code + LIVE ✓ confirmed] Primary index field list omits 7 fields the transformer reads → priority/labels/resolution/reporter/storyPoints/created/updated blank on fresh index (self-heals ~1h via refresh fallback).** `jira-fields.js:48-63`. **LIVE: issue with `priority=High` + label `harness-m10` → fresh index stored `priority=null labels=[]` (`index-fields.spec.ts`).** Fix: add the 7 fields to `getIndexFields()`.
- **M11 [code + LIVE ✓ confirmed] Incremental updater computes deps/parent/children against the FIRST plan's key set, then writes that issue into EVERY plan → corrupts other plans' dependencies.** `incremental-updater.js:35-48`. **LIVE: Q blocks X; Plan A={X}, Plan B={X,Q}; before, Plan B's X.predecessors=[Q]; after invoking the real `incrementalUpdateIssue(X)`, Plan B's X.predecessors=[] — the X→Q dependency was wiped (`incremental-update.spec.ts`; hook gained an `incrementalUpdate` action).** Fix: re-transform per plan with that plan's own keys (move `transformIssue` inside the loop).
- **M12 [code] Incremental updater passes only `{fields}` to transformIssue → loses configured link type → can wipe dependencies on instances with a non-Blocks link type.** `incremental-updater.js:40`. Fix: pass full `loadConfig()`.

## Live-repro constraints (code-verified; NOT reproduced live — honest, not flaky)
These remain `[code]`-solid but reproducing them on wolfaenpak is impractical / out-of-scope / config-gated:
- **M1** — apply-time conflict check is fail-open (client never calls `saveDraft`; detector never re-reads Jira). Needs the write-back resolver path + 2 actors (A stages, B edits in Jira). Not hook-reachable.
- **M2** — `completeWrite` returns success + bumps version even when `verifyWrittenIssues` reports mismatches. `verifyWrittenIssues` (detection) works; `completeWrite` (the resolver, lines 145-175) has no `mismatches` branch — but it's a frontend-bridge resolver entangled with locks/chunks, not cleanly hook-invokable. Code-verified; live-repro needs invoking `completeWrite`.
- **M3 / M4** — write-lock ownership / TOCTOU. Need TWO simultaneous writers (concurrent `startWrite`/`writeChunk`) within the KVS read-write window. Single-actor REST can't force the race.
- **M9** — `updateIssuesInShards` "batch of 5" throttle is a no-op (all fire at once). Throughput/throttling concern, NOT a correctness failure — no observable wrong output.
- **M12** — incremental updater passes only `{fields}` → loses the configured link type → falls back to `'Blocks'`. **Only bites on a NON-default `dependencies.linkTypeName`. wolfaenpak uses the default "Blocks", so it does NOT reproduce here** (the fallback equals the real value). Real for instances with a custom link type.
- **B4** — `getBoardIssues` `startAt += 100` skips issues / loops. Needs an Agile board source with >100 issues. Not set up.
- **m2** — re-indexing a shrunk plan orphans higher-numbered shards. Bounded storage leak, no read-correctness impact; verifiable only via a KVS prefix scan the hook doesn't expose.
- **m3** — `saveAllIssues` O(n²) shard assignment. Perf-only, not a failure.
